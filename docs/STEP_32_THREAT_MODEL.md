# CHAKRVIEW — STEP 32 THREAT MODEL
## Secure Federation Session & Key Lifecycle Hardening

### Status
- **Step**: 32
- **Scope**: Lifecycle threat modeling for peer sessions, Ed25519 identity key rotation, TLS certificate rotation, replay defenses, revocation cascades, and frozen neural invariants.

---

## 1. Threat Matrix & Formal Mitigations

| Threat ID | Threat Description | Attack Vector | Severity | Mitigation & Architectural Guarantee |
| :--- | :--- | :--- | :--- | :--- |
| **T1: Stale Session Hijacking** | Attacker utilizes an expired session ID to execute capability requests. | Inject expired session ID into wire envelope header. | **CRITICAL** | **Fail-Closed Epoch Validation**: `SecurePeerSession.is_active()` evaluates logical epoch bounds. Expired sessions automatically transition to `EXPIRED`, emit `STALE_AUTHORIZATION_DENIED` audit events, and raise `CrossZoneAuthorizationError`. |
| **T2: Indefinite Session Extension** | Peer repeatedly requests session renewal to maintain permanent authorization. | Continuous session renewal requests without re-authentication. | **HIGH** | **Bounded Lifetime Ceilings**: Sessions enforce `max_lifetime_epochs = 200` and `max_renewals = 5`. Exceeding either ceiling raises `SessionTransitionError`. Furthermore, renewal boundary is hard-capped by `TrustGrant.expires_epoch`. |
| **T3: Identity Key Substitution** | Malicious peer claims a new key without proving ownership of the old key. | Submitting unverified public key to `rotate_peer_key()`. | **CRITICAL** | **Atomic Rotation Proof**: `rotate_peer_key()` requires an Ed25519 signature over `ROTATE_KEY:{old_fp}:{new_fp}:{epoch}` generated by the existing registered private key. Invalid signatures raise `SignatureVerificationError`. |
| **T4: Retired Key Signature Replay** | Attacker intercepts and replays wire messages signed by a superseded key. | Sending envelopes signed with previously rotated keys. | **HIGH** | **Retired Key Ledger**: `CryptographicPeerIdentity` retains retired key fingerprints and wrappers in `retired_keys`. The engine explicitly rejects envelopes signed by any retired key with `SignatureVerificationError`. |
| **T5: Certificate Re-binding Spoofing** | Attacker presents an arbitrary TLS certificate to hijack peer identity. | Rotating certificate to an invalid, revoked, or untrusted cert. | **CRITICAL** | **Hermetic Validation & Binding**: Replacement certificates are validated against validity dates, SAN/CN match, and `CertificateRevocationRegistry` before binding via `PeerCertificateBinder`. |
| **T6: Capability Escalation via Renewal** | Peer attempts to gain ungranted scopes during renewal or key rotation. | Embedding escalated scope claims in renewal payloads. | **CRITICAL** | **Scope Immutability (`SESSION_RENEWAL != CAPABILITY_ESCALATION`)**: Session renewal and key rotation only advance epoch bounds; capability scopes and permissions remain strictly governed by the local `CrossZoneFederationPolicy` and `CapabilityGate`. |
| **T7: Trust Revival via Rotation** | Peer with expired trust grant attempts to revive trust by rotating its key or certificate. | Calling key/cert rotation to reset trust status. | **CRITICAL** | **Trust Orthogonality (`KEY_ROTATION != TRUST_RENEWAL`)**: Trust grants are governed independently by `TrustModel`. Expired trust blocks session renewal and capability execution, regardless of key or certificate state. |
| **T8: Cross-Tenant Boundary Violation** | Peered tenant sends requests targeting unauthorized local tenants across renewed sessions. | Specifying foreign `target_tenant_id` in wire envelope payload. | **CRITICAL** | **CrossZoneIsolationGuard**: Evaluated on every request before execution. Strict tenant isolation cannot be bypassed by session renewal or identity rotation. |
| **T9: Wire Replay & Sequence Manipulation** | Attacker replays historical wire envelopes or sends out-of-order payloads. | Replaying captured envelopes or interleaving duplicate sequence IDs. | **HIGH** | **Bounded Replay Cache & Monotonic Sequences**: Sessions maintain a bounded FIFO cache (`max_message_history = 1000`) and enforce strict sequence monotonicity. Replays raise `ReplayAttackError`. |
| **T10: Revocation Cascade Bypass** | Revoked peer continues executing requests using active pre-existing sessions. | Sending requests on pre-established sessions after peer revocation. | **CRITICAL** | **Deterministic Revocation Cascade**: `revoke_peer()` atomically revokes peer registry, key state, all associated sessions (`sess.revoke()`), and deactivates certificate bindings. All subsequent requests fail closed. |
| **T11: Secret & Credential Exposure** | Sensitive keys or raw credentials leak into audit logs, error messages, or traces. | Inspecting audit logs, trace records, or object `__repr__`. | **HIGH** | **Zero-Leakage Architecture**: Private keys and symmetric secrets are strictly excluded from `repr()`, `str()`, `to_dict()`, and audit telemetry. Only non-sensitive fingerprints and IDs are recorded. |
| **T12: Neural Weight Modification** | Federation message triggers side-effects modifying neural weights. | Payload exploiting capability gate or execution engine to alter model weights. | **CRITICAL** | **CoreIntegrityGuard (ΔW = 0)**: Cryptographic SHA-256 weight hash verified before and after every cross-zone execution. Any variation raises `WeightMutationDetectedError` and aborts immediately. |

## 2. Invariant Verification Summary

All 12 threats are verified by deterministic automated tests in `tests/test_session_key_lifecycle.py` and benchmarked in `scripts/benchmark_session_key_lifecycle.py`.
Zero vulnerabilities or bypasses are permitted.
