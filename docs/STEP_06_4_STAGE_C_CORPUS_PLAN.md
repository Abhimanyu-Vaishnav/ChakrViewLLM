**Document Version**: 1.0.0  
**Status**: APPROVED DESIGN GATE — READY FOR IMPLEMENTATION

---

## 1. Scope

This specification establishes the architectural, licensing, quality, and scaling plan for **Stage C: Large-Scale Open-Source Pre-Training Corpus Engineering**.

Step 6.2 and Step 6.3 proved that:
1. The end-to-end data pipeline (cleaning, normalization, tokenization, atomic sharding, streaming reader, causal loss, AdamW, checkpointing, and deterministic resumption) is functional and verified by 247 green tests.
2. The Stage B corpus (501,653 tokens) was **synthetically generated in Python via template combinations**, making it suitable for pipeline validation, but unsuitable as a true pre-training corpus.

Step 6.4 serves as the **Design Gate** governing the acquisition, filtering, licensing, balancing, and sharding of real-world, permissively licensed open data before executing large-scale downloads or training runs.

## 3. Stage C Goals

1. **Replace Synthetic Data with Authentic Text**: Transition 100% of pre-training tokens to genuine, human-authored and open-source programming text.
2. **Strict Provenance & Licensing**: Admit only sources with unambiguous, permissive, commercial/training-compatible licenses (CC0, MIT, Apache 2.0, Public Domain, CC-BY 4.0).
3. **Bilingual Indigenous Priority**: Balance Hindi (Devanagari) and English as primary linguistic pillars, supported by Code, Mathematics, Hinglish, Sanskrit, and Structured Logic.
4. **Hardware & Compute Feasibility**: Scale to a token budget that can be trained and validated on local CPU within predictable runtime bounds.
5. **Deterministic Pipeline**: Guarantee bit-for-bit reproducible data ingestion, cleaning, deduplication, and sharding.

## 6. License & Provenance Governance Policy

1. **SPDX Mapping**: Every document admitted must carry a recognized SPDX identifier (`CC0-1.0`, `MIT`, `Apache-2.0`, `PSF-2.0`, `CC-BY-4.0`, `CC-BY-SA-4.0`, or `Public-Domain`).
2. **Attribution Preservation**: Sources requiring attribution (CC-BY, CC-BY-SA) will be documented with upstream URL and author in [docs/CHAKRVIEW_CORPUS_DATA_CARD.md](file:///d:/Project/ChakrView/docs/CHAKRVIEW_CORPUS_DATA_CARD.md).
3. **No Inferred Licenses**: Repositories without explicit `LICENSE` files or official copyright notices will be marked `UNKNOWN` and rejected.

## 7. Acquisition Strategy

All source downloads must be deterministic and verifiable:

```
[Official Dump / Pinned Git Tag]
               │
               ▼  (Verify SHA-256 Checksum)
       [data/sources/raw/]
               │
               ▼  (Deterministic Extraction: XML/JSON/HTML -> Plain Text)
       [data/sources/extracted/]
               │
               ▼  (Clean, Validate, Filter, Deduplicate)
          [data/raw/]
```

* **Version Pinning**: Wikipedia dumps will be pinned to an exact release date (e.g. `2026-09-01`). Git repositories will be pinned to exact commit SHA hashes.
* **Archive Hash Verification**: Download scripts will check SHA-256 digests against pinned values before extracting.
* **Extraction Discipline**: Standard library parsers (`xml.etree.ElementTree`, `json`) only. No dynamic scrapers executing JavaScript.

## 8. Data Quality Policy

Incoming text will undergo two sequential filter tiers:

### 8.1 Tier 1: Syntax & Character Health (Automatic Rejection)
1. **UTF-8 Validity**: Reject any sequence causing `UnicodeDecodeError` or containing replacement character `\uFFFD`.
2. **Zero Null Bytes & Controls**: Immediate discard if containing `\x00` or ASCII controls in ranges `0x00–0x08`, `0x0B–0x0C`, `0x0E–0x1F`, `0x7F`.
3. **Devanagari Semantic Preservation**: Must preserve combining characters (`\u0901`–`\u0903`), nukta (`\u093C`), virama/halant (`\u094D`), and explicit joiners (ZWJ `\u200D`, ZWNJ `\u200C`).
4. **Length Bounding**: Document character count must satisfy $20 \le \text{length} \le 10,000$.

### 8.2 Tier 2: Heuristic & PII Filtering (Automatic Discard / Scrub)
1. **PII Regex Scanners**: Discard any document containing phone numbers, Aadhaar patterns, credit card formats, or private email address blocks.
2. **Repetition Throttling**: Discard documents with any single character repeated consecutively $>15$ times, or identical lines repeated $>3$ times.
3. **Wikipedia Boilerplate Removal**: Strip reference brackets (`[1]`, `[citation needed]`), category footers, and edit links.
4. **Code Quality**: For Python files, verify parseability via `ast.parse()`. Drop unparseable snippets.

## 9. Deduplication Strategy

To prevent overfitting on a 3.4M parameter model, deduplication operates in three distinct phases:

1. **Exact Document Deduplication**:
   * Compute SHA-256 of `clean_training_text(doc)`.
   * Discard any subsequent document with an identical hash.
2. **Exact Line Deduplication**:
   * For documentation and code, eliminate repeated identical lines (license disclaimers, repeated import statements) exceeding 2 occurrences across a source.
3. **Near-Duplicate Pruning via 64-bit SimHash**:
   * Compute 64-bit character 5-gram SimHash.
   * If Hamming distance between two document fingerprints is $\le 3$, prune the shorter document.
   * Total memory for 100k documents: $\sim 800\text{ KB}$ (fits in L2 cache).

## 11. Split Strategy

* **Split Proportions**: **85% Train / 7.5% Validation / 7.5% Test**.
* **Pre-Tokenization Document Partitioning**: Partition documents before tokenization to ensure zero leakage.
* **Deterministic Hashing**: Assign split using:
  $$\text{bucket} = \text{SHA256}(\text{doc\_id}) \pmod{1000}$$
  * $0 \le \text{bucket} < 850 \implies \text{Train}$
  * $850 \le \text{bucket} < 925 \implies \text{Validation}$
  * $925 \le \text{bucket} < 1000 \implies \text{Test}$
* **Cross-Split Disjointness**: Automated assertion that $\text{Train} \cap \text{Val} = \emptyset$ and $\text{Train} \cap \text{Test} = \emptyset$.

## 13. Decision & Technical Recommendation

### Recommendation: **Option A (10M Tokens) for Stage C.1 Milestone**

**Engineering Rationale**:
1. **Capacity Alignment for 3.4M Parameters**: For a micro model with 3.44M parameters, 10M tokens provides approximately 2.9 tokens per parameter. This is mathematically sufficient to ground the basic vocabulary, syntax, and bilingual token transitions without overfitting or stalling training.
2. **CPU Execution Feasibility**: At 1.1 hours per epoch, a full pre-training run can complete, evaluate, and save checkpoints in a single afternoon session without thermal throttling or multi-day risk.
3. **Auditability**: 10M tokens represents approximately 50,000–80,000 documents across 40 shards. This scale permits complete manual and programmatic inspection of data cards, licenses, and manifests.
4. **Phased Expansion Path**:
   * **Stage C.1 (10M Tokens)**: Initial authentic multi-domain pre-training baseline.
   * **Stage C.2 (25M Tokens)**: Extended training if Stage C.1 loss continues descending smoothly without plateauing.

## 15. Risks & Mitigation

1. **Risk: Indic Script OCR / Corrupted Halants**
   * *Mitigation*: Run `validate_devanagari_encoding()` from `chakrview/corpus/validators.py` on all Hindi and Sanskrit extracts.
2. **Risk: Wikipedia Quality Variance**
   * *Mitigation*: Apply strict length ($>100$ characters) and printable ratio ($>85\%$) thresholds to discard stub articles.
3. **Risk: Code Repositories Containing Secrets / Private Keys**
   * *Mitigation*: Run regex secret scanner before admitting any code file.
4. **Risk: Overfitting on Small Corpus**
   * *Mitigation*: Enforce weight decay (0.01) and evaluate train vs validation cross-entropy gap every 250 steps.
